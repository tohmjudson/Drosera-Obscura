# Drosera2026 — Daisy Seed Audio Engine

Firmware for the Electrosmith Daisy Seed that generates sound for the
Drosera head. It talks to the ESP32 Feather (the "Drosera Head
Controller") over a simple UART text protocol and has no knowledge of
OSC, Wi-Fi, servos, or any other part of the robot — its only job is to
listen for `<id> <value>` commands and make sound.

This project is intentionally split into two halves:

- A small **protocol core** (UART parsing, link/reset handling, CPU
  telemetry) that the robotics side depends on and that should not be
  changed.
- A **swappable synth engine** that a separate team (musicians/sound
  designers) can replace entirely with their own code, via a single
  flag — no knowledge of UART, the Feather, or the robot required.

This README is written for a developer setting this project up for the
first time on **macOS**. Windows steps are noted where they differ, with
a link to Electrosmith's official docs for the parts that are
OS-specific.

> **Physical assembly / wiring:** the Feather and Daisy Seed mount on a
> custom board with labeled audio output terminals — there is no
> point-to-point wiring to do by hand. This README covers only software: the
> toolchain, the project, and the two-engine system.

## Quick-start checklist

If you've done this before and just need the sequence:

1. Install the Daisy toolchain once per machine (§3).
2. Confirm `Drosera2026/` sits inside `DaisyExamples/MyProjects/` (§3.3, §4).
3. Decide which engine you want active and set the flag in
   `EngineConfig.h` (§2.3).
4. Open the project in VS Code, put the Seed in DFU mode, `Cmd+Shift+B`
   (§5).
5. Press RESET on the Seed.
6. Confirm sound, and confirm the Feather sees the Daisy as online
   (§5.5) — or bench-test standalone without the Feather at all (§5.6).

If anything in that list doesn't make sense yet, read the full sections
below once — after that, this list is all you'll need.

## 1. What this project is

| | |
|---|---|
| Hardware | Electrosmith Daisy Seed |
| Framework | libDaisy + DaisySP (official Electrosmith C++ libraries) |
| Communicates with | ESP32 Feather via UART (TX/RX only, 115200 baud) |
| Demo audio engine | `HybridEngine` (FM bell/chime, one-shot) and `ChirpEngine` (filtered noise burst sequencer), in `synth_engine.h` |
| Student audio engine | `StudentEngine`, in `student_engine.h` — a blank-slate starting point with a basic working sine-beep |
| Engine selection | One `#define` in `EngineConfig.h` |
| Build system | Make, via VS Code tasks generated by the Daisy toolchain installer |

The Feather sends plain-text lines like `17 1\n` (parameter ID, then
value). Drosera2026 parses each line and either:

- hands it to the **protocol core** directly, if it's a reserved
  link/reset ID (see §2), or
- forwards it to whichever **synth engine** is currently active.

Every audio sample, the active engine's output is mixed and sent to the
Seed's audio output, and the Daisy periodically reports its own CPU load
and link heartbeat back to the Feather regardless of which engine is
running.

For the full list of parameter IDs and what they do, see **§6 Protocol
Reference**. For how to write and enable your own engine, see **§2**.

## 2. Two engines, one flag

### 2.1 Why it's built this way

The robotics team and the sound/music team are different people working
at different times, with different skills. The robotics side needs the
Daisy to reliably answer a link-health ping and report its status no
matter what sound it's making. The music side needs to write sound code
without having to learn UART, OSC, or the rest of the robot.

So the Feather is deliberately **not** locked down about what it sends
to `/daisy` — any numeric parameter ID and value can be sent, and it's
up to the Daisy-side engine to decide what, if anything, that ID means.
This is by design, not an oversight.

### 2.2 The one rule: reserved IDs

A small set of IDs are the **wire protocol**, not synth parameters. They
are handled in `Drosera2026.cpp` *before* either engine ever sees the
message, and no engine — demo or student — can intercept, redefine, or
break them:

| ID | Direction | Meaning |
|---:|---|---|
| `97` | Feather → Daisy | Soft reset |
| `99` | Feather → Daisy | Link ping — sent periodically; **must** get a reply or the Feather marks the Daisy offline |
| `50` | Daisy → Feather | CPU load |
| `51` | Daisy → Feather | Ready (boot / after reset) |
| `52` | Daisy → Feather | Heartbeat (reply to ping) |
| `53` | Daisy → Feather | Status / unknown-ID echo |

**Never reuse IDs 50, 51, 52, 53, 97, or 99 for anything else**, in
either engine. Every other ID — `0–49` and `54–96` — is open and belongs
entirely to whichever engine is active.

### 2.3 Switching engines

Open `EngineConfig.h`:

```cpp
#define USE_STUDENT_ENGINE 0   // 0 = demo engine (synth_engine.h)
                                // 1 = student engine (student_engine.h)
```

Flip the value, rebuild, and reflash (§5). That's the entire process —
`Drosera2026.cpp` branches on this flag in exactly three places
(engine instance, `AudioCallback`, and `ProcessMessage`/`SoftReset`), and
nothing else in the file needs to change either way.

### 2.4 Writing a student engine

`student_engine.h` ships with a small working example — a sine-wave
"beep" with four parameters — rather than a silent stub, so the project
makes sound the first time you build it with the flag set to `1`.

| ID | Parameter | Value | Notes |
|---:|---|---|---|
| 1 | Pitch | MIDI note, 0–127 | A4 = 440 Hz |
| 2 | Volume | 0–127 → 0.0–1.0 | |
| 3 | Duration | milliseconds | note auto-stops after this long |
| 4 | Trigger | 1 | starts a new note |

The required interface is deliberately small:

```cpp
void Init(float sampleRate);           // called once at startup
void HandleParam(int id, int value);   // called once per received message
void Update(uint32_t now);             // called every main-loop iteration
float Process();                       // called once per audio sample
```

You're free to:

- Delete the example sound entirely and replace it with your own.
- Use any IDs in `0–49` or `54–96` and have them mean anything you want.
- Add as many parameters, voices, or effects as fit in the Seed's CPU
  budget (watch outbound ID 50 — see §7 Troubleshooting).

You're not free to:

- Touch IDs `50, 51, 52, 53, 97, 99` — these are handled outside your
  engine entirely and your `HandleParam` will never even receive them.
- Block or busy-wait inside `Process()` — it runs once per audio sample
  inside the real-time audio callback.

**Keep your own ID table up to date.** Because IDs can mean anything in
your engine, `student_engine.h` has a comment block at the top for you
to document your own parameter map — treat it as the source of truth
for anyone on the robotics side who wants to trigger your sounds from a
touch sensor, button, or AUTO-mode event. An out-of-date table is the
most likely source of confusion between the two teams.

## 3. One-time toolchain setup (macOS)

This project assumes you installed the Daisy toolchain the standard way,
via Electrosmith's official examples repo. If you've already done this
once on your machine, skip to **§4**.

1. Clone the official examples repo somewhere convenient (this is *not*
   the same folder as this project — it's the toolchain installer and a
   sibling to where your own projects will live):

   ```bash
   git clone --recursive https://github.com/electro-smith/DaisyExamples.git
   cd DaisyExamples
   ```

2. Run the setup script. This installs the ARM embedded toolchain,
   `dfu-util` (used for flashing over USB), VS Code (if not already
   installed), and the recommended VS Code extensions:

   ```bash
   sh setup_mac.sh
   ```

3. Confirm you now have `libDaisy/` and `DaisySP/` built, sitting
   **alongside** a `MyProjects/` folder:

   ```text
   DaisyExamples/
   ├── libDaisy/
   ├── DaisySP/
   ├── MyProjects/
   │   └── Drosera2026/        <- this project lives here
   └── ...
   ```

   This matches the relative paths in this project's `Makefile`
   (`LIBDAISY_DIR = ../../libDaisy/`, `DAISYSP_DIR = ../../DaisySP/`),
   so **Drosera2026 must stay inside `MyProjects/`** for the build to
   find the libraries without edits.

> **Windows:** the equivalent script is `setup_win.ps1`. Follow
> Electrosmith's official guide for Windows-specific driver and PATH
> setup: https://github.com/electro-smith/DaisyWiki/wiki/1.-Setting-Up-Your-Development-Environment

## 4. Getting this project set up

If `Drosera2026/` isn't already in `MyProjects/`, place it there now so
the folder layout matches §3. The folder should contain:

```text
Drosera2026/
├── Drosera2026.cpp
├── EngineConfig.h
├── synth_engine.h
├── student_engine.h
├── Makefile
└── .vscode/
    ├── tasks.json
    └── launch.json
```

The `.vscode/tasks.json` and `launch.json` files are generated by the
Daisy toolchain's project template — if this folder was created by
copying one of the `DaisyExamples` template projects (or by the
toolchain's `make_new_project` helper), they're already correct and you
shouldn't need to touch them.

Open the project folder directly in VS Code (not the whole
`DaisyExamples` repo):

```bash
code DaisyExamples/MyProjects/Drosera2026
```

## 5. Building and flashing (first-time walkthrough)

### 5.1 Hardware connection

- Connect the Daisy Seed to your Mac via USB.
- To put the Seed into **DFU (bootloader) mode** for flashing:
  1. Hold the **BOOT** button.
  2. While still holding BOOT, tap **RESET**.
  3. Release **BOOT**.
  - The Seed is now in DFU mode and ready to receive a new program. It
    will stay this way until reset again or power-cycled.

### 5.2 Build + flash via the menu (what you're doing now)

1. In VS Code, open the top menu: **Terminal → Run Task...**
2. Select **`build_and_program_dfu`**.
3. VS Code will compile the project and then invoke `dfu-util` to flash
   it over USB. Watch the integrated terminal for `Download done.` and
   confirm there are no errors.
4. Press **RESET** on the Seed once flashing completes to run the new
   program.

### 5.3 A simpler way: keyboard shortcut

The Daisy project template marks `build_and_program_dfu` as the
**default build task**, so you don't need the menu at all:

```text
Cmd+Shift+B
```

This runs the exact same task as §5.2 with one keystroke. If
`Cmd+Shift+B` ever prompts you to *choose* a task instead of running it
immediately, open `.vscode/tasks.json` and confirm
`build_and_program_dfu` has:

```json
"group": { "kind": "build", "isDefault": true }
```

### 5.4 Command-line equivalent (optional)

If you prefer the terminal directly instead of VS Code tasks:

```bash
cd DaisyExamples/MyProjects/Drosera2026
make clean
make
make program-dfu
```

(Remember to put the Seed back into DFU mode per §5.1 before
`program-dfu` — the Makefile does not do this for you.)

### 5.5 Confirming it worked

With the Feather powered and wired to the Seed's UART pins, open the
Feather's Serial Monitor (115200 baud) — you should see Daisy ready/
heartbeat activity once the link is established, and the Feather's OLED
Daisy status page (`displayMode 4`) should start showing live CPU load
within a couple of seconds of boot. This happens identically regardless
of which engine (`EngineConfig.h`) is active — the protocol core doesn't
care what's making sound.

### 5.6 Testing your engine without the Feather or the robot

You don't need the robot assembled, or even the Feather powered, to
test a sound engine — the Daisy only needs `<id> <value>\n` lines sent
to its UART RX pin at 115200 baud. If you have a USB-to-TTL serial
adapter (same kind used for Arduino/ESP32 bring-up):

1. Connect adapter **TX → Daisy pin 15 (RX)**, adapter **RX → Daisy pin
   14 (TX)**, and a shared **GND** — the same two signal pins the
   Feather normally talks to on the carrier board.
2. Open a serial terminal at 115200 baud (VS Code's built-in terminal
   doesn't do raw serial — use a tool like `screen`, `minicom`, CoolTerm,
   or the Arduino IDE's Serial Monitor pointed at the adapter's port).
3. Type a line and press enter, e.g. for the student starting example:

   ```text
   2 100
   1 69
   4 1
   ```

   (volume 100, pitch = A4, trigger) — you should hear the beep
   immediately.
4. You'll also see the Daisy's own outbound traffic in the same
   terminal — `51 1` on boot, `50 <load>` every ~200ms, and `52 <n>` if
   something sends it a ping. This is a convenient way to watch the
   protocol core working without any robot hardware at all.

This is the recommended way for the music/sound team to develop and
test an engine independently, in parallel with the robotics team's
work on the Feather.

### 5.7 Debug logging (no debug probe required)

`launch.json` assumes a hardware debug probe (e.g. ST-Link) for
breakpoint debugging, which most students won't have. Without one,
there's no `printf`-to-console available over USB — but you can log
values the same way the protocol already does: send them as a
status message.

```cpp
SendMessage(ID_STATUS, someIntValue);  // shows up as "53 <value>"
```

Watch for it in the Feather's Serial Monitor, or directly in a
terminal via the standalone bench setup in §5.6. It's crude (one int at
a time, and it shares an ID with real unknown-command errors) but it's
immediate and requires no extra hardware — the standard way to answer
"what value is my code actually seeing?" on this platform.

## 6. Protocol Reference

The Daisy listens for ASCII lines of the form `<id> <value>\n` over
UART and responds the same way. Reserved IDs are handled in
`Drosera2026.cpp`; everything else is handled inside whichever engine
is currently active (§2).

### 6.1 Reserved — protocol core (same regardless of engine)

| ID | Direction | Meaning | Notes |
|---:|---|---|---|
| 50 | Daisy → Feather | CPU load, 0–100 | sent every ~200 ms |
| 51 | Daisy → Feather | Ready | sent once, on boot or after soft reset |
| 52 | Daisy → Feather | Heartbeat counter | sent in reply to each ID 99 ping |
| 53 | Daisy → Feather | Status / unknown-ID echo | sent on unrecognized ID or malformed line |
| 97 | Feather → Daisy | Soft reset | re-inits the active engine and master volume |
| 99 | Feather → Daisy | Link ping | **not** a reset — Daisy must reply with ID 52 |

### 6.2 Demo engine (`synth_engine.h`) — active when `USE_STUDENT_ENGINE 0`

**Bell / Chime engine (`HybridEngine`)**

| ID | Parameter | Value | Notes |
|---:|---|---|---|
| 11 | Amplitude | 0–127 → 0.0–1.0 | |
| 12 | MIDI note | 0–127 | A4 = 440 Hz |
| 13 | Attack | milliseconds | no clamp |
| 14 | Decay | milliseconds | no clamp |
| 15 | Preset | 0–5 | see table below |
| 16 | Pitch drop | 0 / 1 | ~80 ms exponential glide down on trigger |
| 17 | Trigger | 1 | ignored if a note is already playing (no retrigger) |
| 18 | Detune | cents | random ±value applied per trigger |
| 19 | Stop | 1 | 0.5s speaker-safe fade; stops **both** demo engines |

Presets (ID 15):

| Index | Name | Ratio | Index | Feedback |
|---:|---|---:|---:|---:|
| 0 | Whistle | 1.000 | 0.30 | 0.00 |
| 1 | Soft Bell | 2.756 | 0.80 | 0.00 |
| 2 | Warm Bell (default) | 1.500 | 1.20 | 0.05 |
| 3 | Bright Bell | 3.000 | 1.80 | 0.10 |
| 4 | Metallic Bell | 1.414 | 2.50 | 0.20 |
| 5 | Wood Tone | 3.500 | 1.00 | 0.00 |

**Chirp engine (`ChirpEngine`)**

| ID | Parameter | Value | Notes |
|---:|---|---|---|
| 21 | Chirp duration | milliseconds | length of one chirp |
| 22 | Chirp count | 1–8 | chirps per sequence |
| 23 | Sequence duration | milliseconds | total window; chirps evenly spaced |
| 24 | Filter center | MIDI note 0–127 | A4 = 440 Hz |
| 25 | Amplitude | 0–127 → 0.0–1.0 | |
| 26 | Trigger sequence | 1 | ignored if a sequence is already running |
| 27 | Q | raw float | passed directly to the state-variable filter |

**Master volume**

| ID | Parameter | Value | Notes |
|---:|---|---|---|
| 20 | Master volume | 0–127 → 0.0–1.0 | applied to the mixed output of both demo engines |

### 6.3 Student engine (`student_engine.h`) — active when `USE_STUDENT_ENGINE 1`

Ships with this starting example; **replace this table with your own**
as you change the engine (see §2.4):

| ID | Parameter | Value | Notes |
|---:|---|---|---|
| 1 | Pitch | MIDI note, 0–127 | A4 = 440 Hz |
| 2 | Volume | 0–127 → 0.0–1.0 | |
| 3 | Duration | milliseconds | note auto-stops after this long |
| 4 | Trigger | 1 | starts a new note |

All other IDs in `0–49` and `54–96` are unused by the starting example
and available for you to define.

## 8. Troubleshooting

| Symptom | Likely cause |
|---|---|
| `make` fails with "No such file or directory" for libDaisy/DaisySP | `Drosera2026` isn't inside `DaisyExamples/MyProjects/`, or the repo wasn't cloned `--recursive` |
| `dfu-util` finds no device | Seed isn't in DFU mode — repeat the BOOT+RESET sequence in §5.1 |
| Flash succeeds but nothing happens | Press RESET after flashing; the Seed doesn't auto-run after DFU programming |
| Feather never shows Daisy as online | Check TX/RX aren't swapped between Seed and Feather, that both share a common ground, and that your engine's `HandleParam`/`Process` aren't blocking — reserved IDs are handled before your engine runs, but a hung `Process()` call still stalls the whole audio callback |
| Audio glitches / high CPU load | Watch outbound ID 50 — if it's consistently near 100, a parameter is too expensive for the block size, or too much is overlapping/playing at once |
| Sounds mean different things than expected | Check `EngineConfig.h` — you may be running the other engine than you think. Also confirm the sender (robotics side) and the active engine's ID table (§6.2 or §6.3) actually agree |

## 9. Known limitations

- Parameter values are intentionally unvalidated beyond what each engine
  chooses to clamp — this is by design (see §2.1), not a bug. Extreme or
  malformed values can produce clicks, silence, or unexpected pitches,
  but cannot crash the link protocol itself.
- Demo-engine triggers (ID 17, 26) are simply ignored while a
  note/sequence is already active rather than queued or retriggered.
- The student starting example (§6.3) does not protect against rapid
  re-triggering either — consider this one of the first things worth
  improving.
- `launch.json` assumes a debug probe (e.g. ST-Link) is attached; it is
  not required for the everyday DFU flashing workflow described above.
